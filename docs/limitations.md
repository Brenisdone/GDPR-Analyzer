# Known Limitations and Future Work

## Current limitations

### 1. A technical grade is not a GDPR certification

The overall and module grades are generated by the project's current scoring implementation. They do not establish whether an organization has a lawful basis for processing, valid consent, appropriate retention, complete data-subject-rights workflows, suitable processor agreements, or compliance with every applicable GDPR obligation. Treat results as technical indicators for further investigation, not legal advice.

### 2. Detection coverage is limited

The existing engine reports cookie-related information, web beacon indicators, and transmission-security/TLS information. It does not guarantee exhaustive detection of all trackers, fingerprinting, third-party requests, consent problems, or privacy-relevant behavior.

Static inspection and HTTP-response-based checks can miss behavior that appears only after JavaScript execution, user interaction, consent selection, login, or navigation to other pages. A single target URL is not a crawl of the whole site.

### 3. Empty output is not a verified pass

For example, an empty `cookies.details` object or empty `web_beacons.url` list means the analyzer did not report items in that field for that scan. It does not independently prove that no cookies or web beacons exist. The UI and reports should avoid turning empty or missing data into an unconditional “compliant” or “passed” status.

### 4. Scan execution is synchronous

The API currently runs the scan as part of the HTTP request. A slow target or slow analyzer module can hold a connection open and reduce concurrency. A background queue, bounded worker pool, scan timeout, and explicit `pending`, `running`, `completed`, and `failed` states would improve resilience.

### 5. Server-side request forgery (SSRF) risk

The scanner accepts a URL and makes outbound network requests. Basic URL parsing and IP validation are not a complete SSRF defense. Redirects, DNS rebinding, unusual IP representations, proxy behavior, and DNS changes can bypass simplistic checks or route requests to unintended systems.

Before allowing untrusted users to access the API, implement layered controls:

- Allow only HTTP/HTTPS and explicitly approved ports.
- Resolve and validate all destination IP addresses.
- Validate each redirect destination and limit redirect count.
- Block loopback, private, link-local, multicast, reserved, and cloud metadata ranges.
- Enforce outbound network restrictions at the container or host layer.
- Apply request timeouts, response-size limits, concurrency limits, and rate limits.
- Isolate the scanner from internal services and secrets.

Only scan systems for which you have authorization.

### 6. Local-development deployment is not production-hardened

The current setup is designed for local development. Production deployment would need managed secrets, secure transport, authentication and authorization, database backups, retention rules, monitoring, logging policy, migrations, resource controls, and appropriate network configuration. Do not expose PostgreSQL directly to the public internet.

### 7. No application-level authentication by default

Unless authentication has been added separately, treat the dashboard and API as a trusted local application. A public service needs controls over who may initiate scans and retrieve results or reports, as well as abuse prevention and rate limiting.

### 8. Legacy dependency portability

The original analyzer may depend on older Python packages or platform-specific native libraries. A working Windows development setup does not guarantee the same result on Linux, macOS, or a clean production host. PDF generation is a particular area where native dependencies may be required. Validate setup from a clean environment.

### 9. TLS values need careful interpretation

Protocol, cipher-suite, and certificate values are displayed from the analyzer's output. Their labels, handling of unknown values, and score calculations need to be checked against the engine implementation and current cryptographic guidance. A protocol value such as `YES` indicates the analyzer's reported observation; it does not imply that the protocol is recommended. Preserve unknown/unavailable states instead of translating them into passes or failures without evidence.

### 10. Nested result schema

The API persists a nested JSON object from the legacy engine. Changes to module names or fields can require coordinated updates to the API, dashboard, and report generation. A versioned schema and normalized findings model would reduce coupling and make automated validation easier.

### 11. Scans are not yet a complete crawler or browser audit

Unless the underlying engine specifically implements it, do not assume that the tool navigates all pages, executes all client-side scripts, simulates consent choices, or measures behavior across user sessions. Results apply to the checks performed for the submitted target.

## Recommended next improvements

1. Add automated tests for URL validation, scanner behavior, API routes, database persistence, and report downloads.
2. Add controlled positive/negative test sites for cookie and beacon checks.
3. Normalize findings with category, check, severity, status, evidence, recommendation, and source fields.
4. Document scoring weights, grade thresholds, and treatment of unavailable checks.
5. Harden SSRF controls and isolate outbound scanning.
6. Add background processing, deadlines, and bounded concurrency.
7. Add authentication, rate limits, retention policies, database migrations, and operational monitoring.
8. Verify setup on a clean second machine or reproducible container image.
9. Compare dashboard, JSON, and PDF output for the same saved scan using automated tests.

## Interpretation statement

This is an educational technical-assessment project. It is not a substitute for a comprehensive privacy audit, penetration test, or qualified legal advice.
